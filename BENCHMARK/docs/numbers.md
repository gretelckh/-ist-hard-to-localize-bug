leaked layer (Phase B; `docs/CLUES_49_RESULTS.md`).

## Phase B — runnable diagnostic-clue tool (metrics/diagnostic_clues.py + analyze_clues.py)
- Replaces the leaking `actual_fault_source` intervention with a DETERMINISTIC clue generator that
  classifies the exposure channel and emits DIRECTIONAL guidance, but NEVER names the origin layer
  (verified: no hint asserts an origin).
- Same 80 runs, same LLM. Baseline vs + honest clue vs + leaky channel-label (negative control):
  - **Overall localisation accuracy**: 45.0% -> **52.5% (+7.5 pp)**; leaky-label control **41.2%**.
  - **Per-layer (baseline -> +clue)**: Host 0% -> 19%, Client 0% -> 19%, Server 100% -> 100%,
    Transport 25% -> 25%.
  - **Top-K**: 45/65/85 -> **52/74/94**.
  - Leaky-label control (bare channel label, no guidance) is *worse* than baseline (41.2%) and far
    worse than the honest clue (52.5%) -> the gain comes from the DIRECTIONAL GUIDANCE content, not
    from the channel label, confirming the honest clue does not leak the answer.
- Figure: figs/fig_diag_clues.png; results: data/diag_clues_results.txt + data/diag_clues_metrics.json;
  per-run clues: data/diagnostic_clues.json; LLM answers: data/llm_answers_clues.json /
  data/llm_answers_clues_leaky.json.

## Phase C — repair experiment (metrics/repair_harness.py + analyze_repair.py)
- Does the clue tool help an LLM REPAIR faults (not just localise them)? For each auto-verifiable
  fixable case, the LLM (given the faulting source + SDK output, +/- the clue) produces a fixed
  script, which we re-run and verify (no error + correct value).
- Object set = 23 auto-verifiable fixable cases: synthetic MCP-Fault-20 minus 3 with no observable
  repair effect (c4_wrong_method [method hardcoded], t3_invalid_message [raw-message path masked],
  s7_duplicate_tool_registration [first-wins, no visible change]) = 17, plus 6 advanced production
  bugs. (The real Streamable-HTTP cases are excluded: embedded in HTTP runners, not standalone,
  and their correctness is not auto-verifiable.)
- **Repair success (no-clue vs +clue)**:
  - Synthetic (17): 11/17 = **64.7%** vs **64.7%**
  - Advanced (6): 5/6 = **83.3%** vs **83.3%**
  - **Combined (23): 16/23 = 69.6%** vs **69.6%**
- **Key honest finding**: the clue tool does NOT change repair success when the LLM has the full
  source (it can read the bug directly). This confirms the paper's thesis: the bottleneck in MCP
  debugging is LOCALISATION (clue helps, 45% -> 52.5%), NOT repair once the relevant code is in
  hand (69.6% with or without the clue).
- Figure: figs/fig_repair.png; results: data/repair_results.json / repair_results_clue.json /
  repair_adv_noclue.json / repair_adv_clue.json; summary: data/repair_summary.txt.
